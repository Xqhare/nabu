## Musings

### Add a new `Array` variant

As mused in previous versions, this would be a homogenous array.

There are still several issues:

1. Do all held values keep their type byte?
    - If yes, the disk size will be bigger with superfluous type bytes. Would keep the parser simple though.
    - If no, the disk size will be not that much smaller. Parser could be kept simple with prepending the correct type byte to the buffer?
        - buffer mutation will be not performant though (shifting data).
2. What about simple values? There is no `bool` byte, only `true` and `false`.
    - Simple solution: Simple values are homogenous with each other.
    - Middle ground: define meta groups (single byte values as one group, double byte values as another (null, true, false, nan VS Inf, negInf, PosNan, NegNan)) that are homogenous with each other.
    - Complex solution: Define bytes for `bool`, `complex_number` (infs, nans, null)
        - Needs thought for future expansion capabilities.
3. Interface
    - As it still could be any value, the new `XffValue::SingleArray` would also need `is_*` functions to determine the type.
    - => `xffvalue.into_single_array().unwrap().is_object()` this differs from all other values, an `XffValue::Array::is_object` would always return false.
    - Also access: `xffvalue.as_single_array().unwrap().get(0).unwrap()` would still return a general XffValue by necessity.
- Summary: The access would be verbose, the potential disk size savings small, and the complexity would increase.

All three issues need to be solved before any more real considerations can be made.

### Secure Container

A new single value parent (wrapper essentially), that stores the same values 3 times. Only if 2 of the values are the same, is the value considered secure and thus read and returned. Saturn V style.

Should 3 of 3 agree = Read and return value.
2 of 3 agree = Read and return value. Add possibility to warn the user about degradation for any implementation.
None agree = Error out.

To check, the value does not need to be deserialised, a simple byte match should suffice. (See deterministic byte structure => Consider banning OBJ use and only permit OOBJ here => Would be the only place in the spec where only one value isnt allowed, bad decision)

Very `Array` like, but without the need for an element count.

### Mandatory Metadata

As Xff is primarily designed to store data longterm / archive some metadata should be required to be present.

1. Creation timestamp
2. Last modified timestamp
3. Last read timestamp
4. Author
5. License

1 would be 'read' only. Created during first file write.
2-5 would be 'read and write', mandatory but changeable.

### Hardening

To make Xff better consider this:

In aerospace, satelite transmissions often shuffle the data around before transmitting.
This is because if data is lost / interferred with, the data is corrupted in chunks.
By interleaving and then reassembling the data, the corruption is no longer a single block, but spread across multiple blocks making recovery easier.

NACK - Complexity and performance.

### ECC

As mused about before, it would be good to be able to use ECC to restore the data that was lost.

The large caviat is of course complexity. It would increase the complexity and on disk footprint of xff as well as impacting performance.

Optional. Needs a marker byte and length (length + ECC data checksumed like every other, but with no recovery (ECC block nesting) possible) for every ECC block.
-> `[ECC]([Length][ECC_DATA])[CHECKSUM]`

Protected DATA would look like:
`[DAT]([Length][DATA_BYTES])[CHECKSUM][ECC]([Length][ECC_DATA])[CHECKSUM][EV]`

For values with multiple checksums (Table & Graph), an ECC block would be added for each checksum in the same manner as above.
This retains the non overlapping nature of the data protection.

#### Open consideration: ECC block nesting.

I could use the same rule to add an ECC block to a value to the ECC block itself (the length and ECC data).

`[DAT]([Length][DATA_BYTES])[CHECKSUM][ECC]([Length][ECC_DATA])[CHECKSUM][ECC]([Length][ECC_DATA])[CHECKSUM][EV]`

Here the first ECC block is still error corrected with the second ECC block. Only if both ECC blocks are lost (or the first one beyond repair with the second), the data is lost.

I could allow any nesting depth here. The complexity should remain manageable though.

#### Open consideration: ECC for simple values

As simple values are 1-2 bytes (even if I add many more, they will remain in the 10 byte range at the very most), Adding a full ECC algorithm would be overkill.
Instead, to keep the disk size low, I add an ECC marker followed by the same simple value.

`[TRUE][ECC][TRUE]`

This is probably the best approach, balancing simplicity, disk size and complexity.

It does split up the way ECC works, but the entire type system is divided between simple and complex anyway.

Soft ACK - Really the last feature needed for full usability as a standalone archival format.
