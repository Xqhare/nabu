## Musings

### Add a `Path` value type

To store a path to a file or directory.

I know that utf8 encoding can be problematic, need to dive deeper into this.

### Secure Container

A new single value parent (wrapper essentially), that stores the same values 3 times. Only if 2 of the values are the same, is the value considered secure and thus read and returned. Saturn V style.

Should 3 of 3 agree = Read and return value.
2 of 3 agree = Read and return value. Add possibility to warn the user about degradation for any implementation.
None agree = Error out.

To check, the value does not need to be deserialised, a simple byte match should suffice. (See deterministic byte structure => Consider banning OBJ use and only permit OOBJ here => Would be the only place in the spec where only one value isnt allowed, bad decision)

Very `Array` like, but without the need for an element count.

### Deterministic Byte Structure

Xff is already deterministic, with the important exception of the general Object type.

Really this only needs to be added to the spec as an Info block or similar.

### Mandatory Metadata

As Xff is primarily designed to store data longterm / archive some metadata should be required to be present.

1. Creation timestamp
2. Last modified timestamp
3. Last read timestamp
4. Author
5. License

1 would be 'read' only. Created during first file write.
2-5 would be 'read and write', mandatory but changeable.

### Hardening

To make Xff better consider this:

In aerospace, satelite transmissions often shuffle the data around before transmitting.
This is because if data is lost / interferred with, the data is corrupted in chunks.
By interleaving the first, last, second, second to last etc. and then reassembling the data, the corruption is no longer a single block, but spread across multiple blocks making recovery easier.

To make this easier, Xff should be able to be interleaved and reassembled.

Of course it would then also benefit from ECC to restore the data that was lost.

### ECC

As mused about before, it would be good to be able to use ECC to restore the data that was lost.

The large caviat is of course complexity. It would increase the complexity and on disk footprint of xff as well as impacting performance.
