# `.xff` specification v2

> [!note]
> ***This version is not yet finalized.***

Started work on 2025-03-15;
First draft completed 2025-03-16;
Second draft completed 2025-03-17;

---

`.xff` is a specification for serializing, deserializing and storing data in a binary format.
It is best thought of as a binary JSON variation with error detection.

`.xff` stands for `xqhares file format`, pronounced `squares file format`.

Version 2 is an extension of version 1. 
A version 2 compliant Parser can be constructed in a way to be version 1 compliant as well.

The public API has not changed in any way from version 1.

While this version of the `.xff` specification is designed to be compatible with version 1, several changes have been made that require special attention for implementing a parser compliant with both version 1 and 2 simultaneously. These changes are the way the length is encoded, and the addition of a checksum.

Version 2 uses more disk space than version 1, because of the addition of checksums.\
Every value has increased by 4 bytes in size, and the overall structure increased by 5 bytes.

The binary data in `.xff` is encoded in a custom [ASCII](xff-byte-encoding.md) variation, using `Windows-1252` as its base. \
Any mention of [ASCII](xff-byte-encoding.md) is to be understood to be referring to [this](xff-byte-encoding.md) subset specifically. \
In contrast to version 1, one new entry is added to the [ASCII](xff-byte-encoding.md) character set: `0x17` as `CHK` - Checksum.

`.xff` is capable of holding any kind of data and any amount of it.
The `.xff` format itself has no maximum file size.

The version encoding has changed, but remains backwards compatible with version 0 and 1, [learn more here.](#version-encoding)

A `.xff` file can store seven value types:

1. [Strings](#strings)
2. [Numbers](#numbers)
3. [Data](#data)
4. [Arrays](#array)
5. [Objects](#object)
6. [Boolean's](#boolean)
7. [Null](#null)

All values are delimited with an `EV` marker.

A `.xff` file may never contain zero values.

The diagram below shows the entire composition of a `.xff` file, including the length, version and checksums.

In it are two coloured regions, one in a light blue in the center, and on in light green surrounding it. \
The inner light blue region shows the range of calculation for the value checksum. \
The outer light green region shows the range of calculation for the file checksum. \
All data inside these regions is part of the checksum calculation. \

The inner light blue region also represents the range of calculation for the length of a value.

## Version Encoding

> [!important]
> Any implementation of the `.xff` specification should be able to read and write all versions of the specification, but may choose to support any set of versions or single version and to implement either the ability to read or write, or both.

The version encoding has changed from the previous two versions, but remains backwards compatible with version 0 and 1.

The way the version is encoded is similar to the way the length is encoded in LEB128.
Just as in LEB128, the encoding is variable length and the most significant bit is used as a `continuation bit`.

In contrast to most uses of LEB128, the version is encoded not as a binary number, but as a chain of bits.
The order of the bits is in from least significant to most significant.
The first bit is always part of the version, thus `0` is an acceptable bit and denotes version 0.
All bits set to `1` are added together to form the version.

The last version byte is always padded to a full width byte with `0`.

| Hex | Binary | Version |
| -------------- | -------------- | --------------- |
| 00 | 0000 0000 | 0 |
| 01 | 0000 0001 | 1 |
| 03 | 0000 0011 | 2 |
| 07 | 0000 0111 | 3 |
| 0F | 0000 1111 | 4 |

This means that in practice, the largest version number that can be encoded in one byte is 7 (`0111 1111` in binary). To encode version number 8, two bytes are needed: `0000 0001` and `1111 1111`.

![Chart of the composition of the version in token form.](../pictures/xff_v2-ver-chart.png)

> [!note]
> Instead of parsing the binary data, a simple Hex matching may suffice.

## Checksum
> [!important]
> Any implementation of this specification should be able to read and check the correctness of the data with the checksum of the entire file, as well as with the checksum of single values.
> It must be able to generate and write the correct checksum of the entire file, as well as of single values.

To increase security, as well as to make corruptions more easily detectable, this version of the `.xff` format introduces checksums.
Every value type has a checksum except for `Booleans` and `Null`.

The checksum is a 32-bit unsigned integer and is calculated by using the CRC-32 algorithm.\
The checksum is always 4 bytes long. \
A checksum is delimited from the value by a `CHK` marker. \
The `CHK` marker must appear before the checksum itself.

The checksum of single values is not part of the length field of the value it is contained in.

A checksum calculated by using the data of the value, not including the length field, but including the markers used in `Array` and `Object`.

The file checksum is calculated over the bytes of the entire file, excluding only the version encoding, the `CHK` marker of the file checksum, the checksum itself, and the `EM` marker.

![Chart of the composition of the checksum in token form.](../pictures/xff_v2-chk-chart.png)

### Checksums for zero length arrays and objects
As there is no data to calculate a checksum with, the 4 bytes occupied by the checksum are all set to `0`.

## Length attribute
The length is the amount of bytes the data stream of a value takes up.
Length is an unsigned integer, encoded in binary using the Little-Endian byte-ordering.\
Every value type has a length except for `Booleans` and `Null`. \
Put another way, every value with a checksum has a length.

The way length is encoded has changed drastically form version 1. While still being variable length encoding, it now uses LEB128 encoding of an unsigned integer, instead of the `Length of length` byte.

This means that the most significant bit is reserved as a `continuation bit` and if set to `1`, the next byte continues the length encoding.

The length may be 0 for zero length arrays and objects.

## Strings
A valid `String` is a sequence of a set of [ASCII](xff-byte-encoding.md) characters. Characters `8`-`13`, `32`-`126`, `128`, `130`-`140`, `142`, `145`-`156`, `158`-`255` are permissible.

Strings have to be encoded in [ASCII](xff-byte-encoding.md).\
Character codes 8 through 13 are permissible.\
`String` values may not be empty.

A `TXT` marker is the start of every `String` value.
It is followed by the length of the text in bytes.
Following the length is the text itself, followed by the `CHK` marker and the checksum of the text.
A `String` value is closed by the `EV` marker.

The trailing `EV` marker provides an additional check for correctness, as well as delimiting the value.

The light blue coloured region in the diagram below shows the range of calculation for the value checksum as well as the length of the value.

## Numbers
A valid `Number` is a sequence of decimal digits (`0` to `9`) with no superfluous leading zero, containing at most one '`.`' (period) or '`,`' (comma) decimal separator between digits and beginning with at most one '`-`' (minus sign) to mark a negative number.

'`.`' and '`,`' represent a decimal point. One decimal point is allowed per `Number`. \
'`-`' may only be used as the first character. One minus sign is allowed per `Number`. \
Neither a decimal point marker, nor the minus sign are required to form a valid `Number`. \
The presence of a '`-`' marks the number as negative, the absence of a '`-`' marks the number as positive. \
Neither `NaN` nor `Infinity` is a valid `Number`. \
`Number` values may not be empty.

This specification allows implementations to set arbitrary limits on the range and precision of numbers accepted, but it recommends those set by IEEE754.

A number is opened with the `NUM` marker, followed by the length of the number in bytes, followed by the number itself. 
Behind the number is the `CHK` marker and the checksum of the number.
The number is closed by the `EV` marker.

The trailing `EV` marker provides an additional check for correctness, as well as delimiting the value.

The light blue coloured region in the diagram below shows the range of calculation for the value checksum as well as the length of the value.

![Chart of the composition of a number in token form.](../pictures/xff_v2-number-chart.png)

## Data
`.xff` files can store arbitrary data.\
`Data` values may not be empty.\
All data inside a `Data` value is considered one unified data-stream that is stored as-is and cannot not be changed or manipulated in any way.

Data is opened with the `DAT` marker, followed by the length of the data in bytes, followed by the data itself.
Behind the data is the `CHK` marker and the checksum of the data.
The data is closed by the `EV` marker.

The trailing `EV` marker provides an additional check for correctness, as well as delimiting the value.

The light blue coloured region in the diagram below shows the range of calculation for the value checksum as well as the length of the value.

![Chart of the composition of data in token form.](../pictures/xff_v2-data-chart.png)

## Array
An array may consist of any number of values of any type. The total length of all elements is not limited.\
An `Array` value may be empty. \
Arrays may contain more arrays with no limit set on the amount of nesting.

To open an array, the `ARY` marker is used, followed by the length of the array in bytes, followed by the array itself. 
Behind the array is the `CHK` marker and the checksum of the array.
It is closed by the `EV` marker.

The trailing `EV` marker provides an additional check for the correctness of the value, as well as delimiting the value.

The elements are separated by the `RS` marker.
The array may be closed with a trailing `RS` marker or without.

The light blue coloured region in the diagram below shows the range of calculation for the value checksum as well as the length of the value.

![Chart of the composition of an array in token form.](../pictures/xff_v2-array-chart.png)

## Object
An `Object` may consist of any number of key-value pairs and may be empty.\
Keys must be `Strings` and the values may be of any type.
The keys must be string-encoded as laid out [above](#strings). \
Objects may contain more objects with no limit set on the amount of nesting.

To open an object, the `OBJ` marker is used, followed by the length of the object in bytes, followed by the object itself. 
Behind the object is the `CHK` marker and the checksum of the object.
It is closed by the `EV` marker.

The trailing `EV` marker provides an additional check for the correctness of the value, as well as delimiting the value.

Key-value pairs are enclosed by the `GS` marker, the key and the value are separated by the `US` marker.
The key-value pairs are separated by the `RS` marker.\
The object may be closed with a trailing `RS` marker or without.

The light blue coloured region in the diagram below shows the range of calculation for the value checksum as well as the length of the value.

![Chart of the composition of an object in token form.](../pictures/xff_v2-object-chart.png)

## Musings about a future version 2

### Adding a checksum
To increase the security, as well as to make corruptions more easily detectable, I propose to add a checksum to all data types.
`.xff` was always designed with data storage and transmission in mind. Even while designing version 1, I knew that ideally I would use a checksum.

The checksum is a 32-bit unsigned integer and is calculated by using the CRC-32 algorithm.
This means that the checksum will always be 4 bytes long.

There are two locations and scopes under consideration for the checksum:
1. Adding the checksum to all values, storing it before the `EV` marker.
2. Adding the checksum marker to the file entire file, and storing it before the `EM` marker.

The length of the checksum would not be part of the length field of the value itself.

#### Adding a checksum to all values
Any value that uses the `EV` marker will have the checksum added to it. This excludes all booleans and null.
The proposed location to store the checksum is following the data, but before the `EV` marker.
This checksum would only be calculated by using the actual data of the value, not the length field.

#### Adding a checksum marker to the file
I propose a second checksum, placed at the very end of the file and right in front of the `EM` marker.
This checksum would be calculated over the entire file, including the length field of all values with the only exception being the version encoding and the `EM` marker.

#### Adding a checksum marker
For ergonomics, I would like to add a marker for the checksum.
`0x17` would be the logical choice, as its unused and right in front of the `EV` marker at `0x18`.
I propose to call it `CHK` for checksum.

**ACK** - No-brainer.

### Reworking Length
The length field is needed, but only to decode the `Data` data type.
But there is the chance to rework the way the length is encoded, and make it more bespoke.
I would still want it to be variable length encoded though, to save space.

I do not want to dismiss the possibility of just using 8 bytes for the length always.

The most probable way of reworking length would be to implement LEB128.

**ACK** - Fuck it, we ball. I don't do things because they are easy, but because I think they will be easy!

### Changing the version encoding
Move from a single byte to a more bespoke format. In versions 0 and 1 the version byte is encoded as a single byte unsigned integer. I propose to change it to a chain of bits.

The first bit is always part of the version, thus 0 is an acceptable bit.

If the first bit of the file is 0, its version 0.

If the first bit of the file is 1 and the second bit is 0, its version 1.

If the first bit of the file is 1 and the second bit is 1, its version 2.

The main drawback is the reduction of possible versions representable in a single byte, down to 8.
8 Versions should still be more than enough, and adding on a new byte for version 9 onwards would be trivial with the right standard definition.

#### Reasoning
With removing the length field, I am loosing one of my bespoke features, and to be honest, I want at least one weird, funny or non-standard feature.
I find this incredibly funny for some reason, and I think it would be fun to implement.
Also, I want a reason to need to read single bits, instead of just bytes. Who knows, I might learn something or two!

#### Proposed version encoding standard
The version is encoded not as a binary number, but as a chain of bits.
The order of the bits is in from least significant to most significant, not as a series of bits starting with the very first bit.
The first bit is always part of the version, thus 0 is an acceptable bit and denotes version 0.
For every other versions, every occurrence of a 1 in the bit sequence is a new version.
Should all bits be 1, the next byte is read according to this scheme.
This continues until a bit is 0.

| Binary | Version |
| -------------- | --------------- |
| 0000 0000 | 0 |
| 0000 0001 | 1 |
| 0000 0011 | 2 |

**ACK** - I like it.

### Removing Length in favor of a checksum

The length field is not needed, since the file is self-delimiting. As nice as it was as a kind of verification of data integrity, it was always a lazy man's checksum.

There are two main drawbacks to removing the length field:
1. The minimum size in bytes doubles from 2 to 4.
2. You can no longer just read the length bytes and drain the appropriate number of bytes.

#### 1. The minimum size in bytes doubles from 2 to 4.
Not really a problem, we are talking bytes after all.

#### 2. You can no longer just read the length bytes and drain the appropriate number of bytes.
Again, not really a problem, the xff values are designed to be self-delimiting. But I do really like the ergonomics of it.
But this is my main problem with removing length straight out. It is a stupid and weird thing to do, but I have grown attached to it.

**NACK** - It's actually needed for deserializing the `Data` data-type.
