## Pillars of Design

The `.xff` version 3 specification is built upon three core pillars:

1.  **Universal Integrity**: Every single byte in an XFF file is protected and error-detectable. From marker bytes with parity bits to data blocks with CRC-32 checksums, the format is designed to identify corruption at any level.
2.  **Radical Simplicity**: The format avoids unnecessary complexity, favoring clear structures and self-contained values. This simplicity ensures that implementations are robust, easy to audit, and maintainable over time.
3.  **Data Fidelity Guarantee**: The fundamental promise of XFF is simple: **The data you put in is exactly the data you get out — or you get a clear, predictable error.** General-use implementations must never attempt to "guess," silently truncate, or partially parse malformed data. If an integrity check fails, the parser must halt and report the error to ensure absolute physical and logical integrity (though recovery tools may still attempt to salvage remaining data).

---

`.xff` is a specification for storing structured and unstructured data in a binary format.
It is designed as a binary JSON alternative with a primary focus on universal error detection and high data density.

`.xff` stands for `xqhare's file format`, pronounced `squares file format`.

Version 4 introduces several significant optimizations and features over version 3:
- **Delta Encoding**: All parent offset lists now use delta encoding, reducing the overhead for large collections.
- **Enhanced Simple Value Resilience**: Group 00 markers are remapped to ensure a minimum Hamming distance of 4.
- **Naive Temporal Types**: First-class support for `LocalDate`, `LocalTime`, and `LocalDateTime` to prevent information loss.
- **Graph Parent Type**: Native support for network-based data structures.
- **ASCII-TEXT**: Optimized storage for 7-bit string data.
- **Signed NaNs**: Support for `PNAN` (+NaN) and `NNAN` (-NaN) for lossless math round-tripping.

`.xff` is capable of holding any kind of data and any amount of it. The `.xff` format itself has no maximum file size.

A `.xff` file can store several value types:

1. [Simple Values](#simple-values) (`Null`, `Boolean`, `NaN`, `Infinity`, `Signed NaN`)
2. [Text](#text) (UTF-8 and 7-bit ASCII)
3. [Numbers](#numbers) (`Integer`, `Float`, `Custom Decimal Float`)
4. [Data](#data) (Binary)
5. [DateTime / Duration / UUID](#specialized-complex-types)
6. [Naive Date and Time](#naive-dates-and-times)
7. [Arrays](#array)
8. [Objects](#object)
9. [Tables](#table)
10. [Graphs](#graph)

A `.xff` file may never contain zero values.

## Overall File Structure

A `.xff` v4 file follows the same sequential structure as v3:

1.  **File Signature**: A 4-byte magic number `XFFV` (`0x58 0x46 0x46 0x56`).
2.  **Head**: Contains the version identifier (encoded as `0x0F` for v4) and optional metadata.
3.  **Body**: Consists of exactly **one** single XFF `Value`.
4.  **Terminator**: The `EM` marker.

### File Signature

The file begins with a 4-byte magic number, `XFFV` (`0x58 0x46 0x46 0x56`), used for immediate file type identification.

The magic number is technically made up of two parts, `XFF` and `V`.
`XFF` is an abbreviation for the `.xff` file format, and `V` is a version identifier, as the version encoding immediately follows the signature.

### Head

The head contains the version identifier, followed by the metadata about the file.

#### Version Encoding

The version is encoded using a custom bit-chain variation of LEB128. This encoding is variable length, where the most significant bit (MSB) of each byte serves as a `continuation bit`.

> [!important]
> The version is encoded not as a binary number, but as a chain of bits. The order of the bits is from least significant to most significant. The first bit is always part of the version, thus `0` is an acceptable bit and denotes version 0. All bits set to `1` are added together to form the version number. The last version byte is always padded to a full width byte with `0`.

| Hex | Binary | Version |
| :---: | :---: | :---: |
| 00 | 0000 0000 | 0 |
| 01 | 0000 0001 | 1 |
| 03 | 0000 0011 | 2 |
| 07 | 0000 0111 | 3 |
| 0F | 0000 1111 | 4 |

To encode version number 8, two bytes are required: `1111 1111` (all bits 1, MSB=1 continuation) and `0000 0001` (bit 0 is 1, MSB=0 stop).

#### File Metadata (Optional)

The head may optionally include a single `Metadata` object to provide high-level context. In version 4, the metadata object uses the same delta-encoded structure as introduced to standard objects.

**Structure**: `[META Marker] [Element Count] [Offsets...] [Checksum] [Key/Value Data...] [EV]`

1.  **Constraints**: To simplify parsing of the file head, the metadata object should be **flat-ish**. It may contain parent values (Array, Object, Table), but these parent values **cannot contain further nested parents**. This ensures the metadata block has a predictable, relatively shallow depth.
2.  **Arbitrary Keys**: Any implementation should be able to read any arbitrary metadata key value pairs, and are encouraged to support the standard keys.
3.  **Standard Keys**: Implementations are encouraged to use standard keys: 
  * The value type of all keys is `TEXT`.
  * `creator`: The application or library that generated the file.
  * `created_at`: `DateTime` of creation.
  * `source`: Original source of the data (e.g., a URL or database name).
  * `description`: A human-readable summary of the file content.
  * `license`: The legal license governing the data. The `license` key may be used to store an abbreviated license string or the entire license.
    * Example: `license` = `"MIT"`
    * Example: `license` = `"MIT OR Apache-2.0"`
    * Example: `license` = `"Copyright (c) YEAR Copyright Holder. Permission is hereby granted ..."`

## Integrity System

Version 4 maintains the two-tier integrity system while enhancing the lightweight check.

### 1. Lightweight Check (Enhanced Parity)

The MSB of every marker byte is an even parity bit. In version 4, the **Simple Value** group (Group 00) has been remapped to ensure a minimum **Hamming distance of 4** between all valid markers. Meaning, that it requires at least 4 bit flips to transform one valid simple value into another valid one.

### 2. Heavyweight Check (CRC-32)

Multi-byte data payloads, including delta-encoded offset lists, are protected by a 4-byte CRC-32 checksum (ISO-HDLC variant, stored in **Little-Endian**).

## V4 Byte-Map

> [!note]
> **Group 00 (Simple Values) Encoding:**
> To ensure a minimum Hamming distance of 4, the Group 00 markers are restricted to 4 optimal byte values. This necessitates a "loose" alignment with the Subgroup bits, as values are grouped by their base marker rather than strict subgroup categorization.
>
> Values are split into single-byte and double-byte (prefixed by `CONT` `0xFF`) forms:
> - **Single-Byte**: `NUL` (0x00), `TRU` (0x87), `FAL` (0x99), `NAN` (0x1E).

## Values

### Length Attribute

The `length` field is used only when a value's size cannot be determined from its marker or encoding. This is specifically the case for `Text` and `Data` value types.

The length is the count of bytes the raw data stream of a value takes up. It is stored as an unsigned integer using LEB128 encoding.

Counting starts immediately after the end of the `length` field. Not included in this count are the bytes occupied by the `length` field itself, the type marker, the checksum, and the `EV` marker.

If the length attribute is present, it is included in the checksum for that value.

### Simple Values

Simple values consist only of their marker byte. They have inbuilt error detection as their MSB is used as a parity bit.

All v4 simple values consist of either one or two bytes.
No length, checksum, or `EV` marker is required.

To achieve a minimum Hamming distance of 4, the Group 00 markers are restricted to 4 values (`0x00`, `0x87`, `0x99`, `0x1E`). To support the 8 required simple values, at most two bytes are required per value. The less used values are encoded using more bytes, using the `CONT` (`0xFF`) byte as a prefix.

- **Single-Byte**: `NUL`, `TRU`, `FAL`, `NAN`.
- **Double-Byte**: `INF`, `NINF`, `PNAN`, `NNAN` (encoded as `0xFF` followed by the base marker for `NUL`, `TRU`, `FAL`, and `NAN` respectively).

Version 4 introduces `PNAN` and `NNAN` for explicit signed NaN support, without implementing any payload mechanism for `NNAN`.

#### Best Practices

While special values (`NaN`, `Infinity`, `NegInfinity` `PositiveNaN`, `NegativeNaN`) are also representable as standard `Float` payloads, doing so is highly space inefficient. A standard `Float` requires 14 bytes (Marker + CRC-32 + 8-byte f64 + EV), whereas using these dedicated markers reduces the footprint down to 1 to 2 bytes.

If special values (`NaN`, `Infinity`, `NegInfinity` `PositiveNaN`, `NegativeNaN`) are rare edge cases and the majority of data is expected to be normal numbers, use the `Float` type.

If these special values are frequent or an expected part of the dataset, utilize these specialized markers to minimize space and reduce encoding/decoding overhead.

Should the payload of a IEEE-754 negative NaN be needed to be stored (to ensure lossless round-tripping of floating-point data from sources like TOML for example), the `Float` Complex Value must be used as the `NNAN` simple value omits support for any kind of payload.

### Complex Values

Complex values store multi-byte data. They contain a CRC-32 checksum and an `EV` marker.

#### Text and ASCII-TEXT

*   **Text (TXT)**: Standard UTF-8 encoded text.
*   **ASCII-TEXT (ASCI)**: Optimized for 7-bit string data.

**Structure**: `[Marker] [Length (LEB128)] [Bytes] [CRC-32] [EV]`

> [!NOTE]
> `ASCI` ignores the MSB of each byte. This value supports true 7-bit ASCII only.
> The parity MSB is omitted as the data integrity is guaranteed by a CRC-32 checksum.

#### Numbers

- **Unsigned Integer (UINT)**: Stored using standard LEB128 encoding.
  - **Structure**: `[Marker] [LEB128 bytes] [CRC-32] [EV]`
- **Signed Integer (SINT)**: Stored using custom LEB128 encoding (v3 style):
  - **Encoding**: To handle signedness, the first byte of the LEB128 sequence uses 2 signal bits: Bit 7 (MSB) for continuation and Bit 6 for signaling (negative/positive). This leaves 6 bits for the initial value fragment. Subsequent bytes follow standard LEB128 (7 bits value, 1 bit continuation).
  - **Structure**: `[Marker] [LEB128 bytes] [CRC-32] [EV]`
- **Float (FLT)**: 64-bit IEEE-754 double-precision number (Little-Endian).
  - **Structure**: `[Marker] [8 raw f64 bytes (Little-Endian)] [CRC-32] [EV]`
- **Custom Decimal Float (CFLT)**: An experimental type using high-precision decimal representation (`HpFloat`).
  - **Structure**: `[Marker] [LEB128 bytes] [LEB128 bytes] [CRC-32] [EV]` (The first LEB128 is the value, the second the scale)

#### Specialized Complex Types

- **DateTime (DT)**: LEB128-encoded Unix epoch (ms since 1970-01-01).
  - **Structure**: `[Marker] [LEB128 bytes] [CRC-32] [EV]`
- **Duration (DUR)**: LEB128-encoded milliseconds.
  - **Structure**: `[Marker] [LEB128 bytes] [CRC-32] [EV]`
- **UUID**: 16-byte raw binary sequence.
  - **Structure**: `[Marker] [16 raw bytes] [CRC-32] [EV]`
- **Data (DAT)**: Arbitrary binary data.
  - **Structure**: `[Marker] [Length (LEB128)] [Raw bytes] [CRC-32] [EV]`

##### Naive Dates and Times

To store non standard date and time values, and to resolve information loss from human-readable formats, v4 adds naive temporal types:

*   **LocalDate (LD)**: `[Marker] [Year (u16 LE)] [Month (u8)] [Day (u8)] [CRC-32] [EV]`
*   **LocalTime (LT)**: `[Marker] [Hour (u8)] [Minute (u8)] [Second (u8)] [Subseconds (LEB128)] [CRC-32] [EV]`
*   **LocalDateTime (LDT)**: `[Marker] [Year (u16 LE)] [Month (u8)] [Day (u8)] [Hour (u8)] [Minute (u8)] [Second (u8)] [Subseconds (LEB128)] [CRC-32] [EV]`

### Parent Values (Delta Encoding)

All parent types in version 4 utilize **Delta Encoding** for their offset lists.

1.  The first offset is stored relative to the start of the `Data Block`.
2.  Each subsequent offset is stored as the difference (**delta**) from the *previous* offset.
3.  Deltas are encoded as LEB128 unsigned integers.

**General Parent Structure:** `[Parent Marker] [Element Count] [Delta Offsets...] [Checksum] [Data Block...] [EV]`

Parent types use an index-based structure to allow for efficient random access without parsing the entire container. This is particularly useful for large datasets where only specific elements need to be accessed and enables multithreaded parsing of child elements. Every implementation is free in how it chooses to leverage (if at all) these structural advantages for reading a file.

Parent types do not have a length field. They instead utilize an `Element Count` and a sequence of offsets. While the `Element Count` determines the number of children, it is a distinct concept from a physical byte length, as child values are accessed via the offset index rather than linear scanning.

#### Array (ARY)
A sequence of anonymous values.

#### Object (OBJ / OOBJ)
A sequence of Key-Value pairs. Keys must be `Text` or `ASCII-TEXT`.

##### Key Order

The `OBJ` value type does not guarantee any particular order for keys. 
If the order is important, use the `OOBJ` type instead. Here, keys must be stored in the same order as they are encountered in the file.

#### Table (TBL)
Optimized structure for row-oriented data with a shared schema.

**Structure:** `[Table Marker] [Column Index] [Column Names] [Row Index] [Element Index] [Row Data] [EV]`

1.  **`[Column Index]`**: `[Column Count (LEB128)]` + `[Column Offsets]` + `[Checksum]`.
    *   `[Column Offsets]`: A sequence of LEB128 offsets, each specifying the start of a column name relative to the start of `[Column Names]`.
    *   `[Checksum]`: A 4-byte CRC-32 (Little-Endian) covering the `[Column Count]` and `[Column Offsets]`.
2.  **`[Column Names]`**: A sequence of `Column Count` `Text` values representing column names.
3.  **`[Row Index]`**: `[Row Count (LEB128)]` + `[Row Offsets]` + `[Checksum]`.
    *   `[Row Offsets]`: A sequence of `Row Count` LEB128 offsets pointing to the start of each row relative to the start of `[Row Data]`.
    *   `[Checksum]`: A 4-byte CRC-32 (Little-Endian) covering the `[Row Count]` and `[Row Offsets]`.
4.  **`[Element Index]`**: `[Element Offsets]` + `[Checksum]`.
    *   `[Element Offsets]`: A sequence of `Row Count * Column Count` LEB128 offsets. Each offset specifies the starting position of a specific cell value relative to the start of `Row Data`.
    *   `[Checksum]`: A 4-byte CRC-32 (Little-Endian) covering the `[Element Offsets]`.
5.  **`[Row Data]`**: The contiguous block of row values. Each row consists of exactly `Column Count` values, matching the order and types implied by the schema. Rows are not individually marked as `Array` or `Object` to save space. Each cell value within `Row Data` is stored as a complete, self-contained XFF value.


#### Graph (GRPH)
A new parent type for network-like data structures consisting of Nodes and Connections.

**Structure:** `[Graph Marker] [Node Count] [Node Offsets] [CRC-32] [Node] … [Node] [Connection Count] [Connection Offsets] [CRC-32] [Connection] … [Connection] [EV]`

##### Node

Both the Payload and Metadata may be any valid XFF value.

The in- and outbound connections are full XFF arrays of connection indices.

**Structure:** `[Node Payload] [Node Metadata] [Array of inbound connections] [Array of outbound connections]`

##### Connection

The first LEB128 value specifies the from node index, and the second LEB128 value specifies the to node index.

The metadata may be any XFF value.

**Structure:** `[LEB128] [LEB128] [CRC-32] [Connection Metadata]`

## End of Value

The `EV` marker (`0x60`) is used to signify the end of a value's physical boundary. 

While technically superfluous for many types where the size is fixed or explicitly defined, it is maintained for consistency and serves as a secondary verification of the stream's logical structure. For **Parent types**, while the `Element Count` could theoretically be used to determine the container's end, the `EV` marker remains mandatory to provide a clear, marker-based boundary for each complex structure.

## End of Medium

The `EM` marker (`0xF0`) signifies the end of the file stream and follows the main body value. While technically superfluous, it is kept to show descendancy from v0 through to v4, and serves as a good practice for stream validation.

## Compatibility Note

As with almost all previous specification versions, version 4 is **not** backwards compatible with byte-streams of previous versions due to:

1.  Remapping of Group 00 markers.
2.  The switch to delta encoding for all parent offset lists.

### First-Class Local Date and Time Support

To resolve the information loss when translating from human-readable formats like TOML, version 4 will introduce dedicated types for "Local" (naive) dates and times. This ensures that a value like `07:32:00` remains a Time and is not accidentally promoted to a Unix epoch or demoted to a raw String.

- **`LocalDate`**: Stores a Year, Month, and Day.
  - **Structure**: `[Marker] [Year (u16 LE)] [Month (u8)] [Day (u8)] [CRC-32] [EV]`
- **`LocalTime`**: Stores Hour, Minute, Second, and Subseconds.
  - **Structure**: `[Marker] [Hour (u8)] [Minute (u8)] [Second (u8)] [Subseconds (LEB128)] [CRC-32] [EV]`
- **`LocalDateTime`**: Following the principle of "Naive = UTC" for simplicity, `LocalDateTime` values could be naively cast to UTC and stored using the existing `DateTime` (`DT`) type. This avoids unnecessary complexity in the value ecosystem while still providing a robust path for naive timestamps.
  - There is a good argument to be made to also add this as its own complex value. Especially since `horae` already supports constructing DateTimes form a utc timestamp and offset anyways(as well as deconstructing into them). Data fidality and all that

Think about LocalDateTime more.

Proposed Markers (Group 01 - Complex):
- `LD` (LocalDate): `0x27` (Even parity)
- `LT` (LocalTime): `0x28` (Even parity)

This expansion directly supports the "Data Fidelity Guarantee" by allowing Mawu and other tools to round-trip TOML data without loss of semantic meaning.

### Signed NaNs (+NaN / -NaN)

The current v3 spec supports `NAN`, `INF`, and `NINF`. However, IEEE 754-2008 technically supports signed NaNs. While often ignored in high-level math, they are crucial for lossless round-tripping of floating-point data (e.g., from TOML) and can carry diagnostic information in the sign bit.

In v4, we should add `PNAN` (+NaN) and `NNAN` (-NaN) as Simple Values.
- `NAN` (Standard/Quiet): `0x14` (already in v3)
- `PNAN` (+NaN): `0x17` (Even parity)
- `NNAN` (-NaN): `0x18` (Even parity)

This ensures that "the data you put in is exactly the data you get out" even for the weirdest edge cases of floating-point math.

For the payload of NaN (if present stored in the fractional bits) cannot be represented as a simple value of one byte. For this reason, v4 will need to ensure that the FLOAT type supports this. (I am very sure of this as I am specifically using IEEE as the base for it; However the serde operations into and outof rust need to be scrutenised for this to be sure.)
ANSWER: To quote the rust std doc: "Primitive Type f64: A 64-bit floating-point type (specifically, the “binary64” type defined in IEEE 754-2008)."

### Pivot 1

With the addition of UUID, DATETIME, true number & text support, as well as the TABLE parent type, the spec is very close to also being a fully usable database format.
This could be expanded - think SQLite for example, one file for the whole database. Easily transferable and maintainable.

This would benefit massively from the ability to read specific values from the file without parsing the entire file.
While already part of the v3 spec, `nabu` does not support this type of parsing, only the entire file.
Keeping track of the needed indexes for the offsets would of course be required but pushed onto the user (`neith`).

This would be in conjunction with the long planned `neith` (database library) rework.

Questions to ponder:

1. What other values are needed or should be supported?
2. The "Footer" or "Index of Indices"
3. Tombstones/Updates: In a DB, we often want to "delete" or "update" a value without rewriting a 2GB file. Would v4 support a "Tombstone" marker (a Simple Value that tells the parser "ignore this offset")?
4. The "Hole" Problem: If you update a value and the new one is smaller, do you leave a "hole" of null bytes? If so, the integrity system (CRC-32) needs to be able to handle "skipped" regions in the data block.

#### 2. footer

In SQLite, the "schema" and "root" of the B-Trees are at known locations. Since XFF is a single-value-root format, if that root is a 1GB Object, you currently have to parse the entire Header + Metadata to even find the start of the Object's index.

Idea: put at absolute end of file, but reverse the leb byte order. Meaning, the last byte of the LEB encoded offset is first, then the second to last as second and so on until the first byte. Variable length, known beginning. Wouldn't need to be checksum protected realistically.
