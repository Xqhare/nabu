## Musings

### Wild Idea 1

I can remove a lot of checksums and make the format smaller.
If I move from LEB-128 to LEB-64 I could use a parity bit to determine if the value is ok.

This can be used for DATETIME, DURATION, NUM UINT, NUM SINT and LENGTH.

Meaning that only NUM FLOAT, UUID, TEXT and DATA would retain a checksum.

To remove more, FLOAT could be reworked to a much simpler 1 byte checksum; E.g. just adding all bits set to 1 (at most 8x8=64 < 255) or similar, same with UUID (at most 16x8=128 < 255) - HOWEVER moving to two different kinds of checksum calc increases complexity

DATA & TEXT (because of their enourmous variablility in length) really benefit from CRC32

For Parents:

Checksum is used to check element count and offsets, if these are also saved as LEB64 then the checksum is not needed.

HOWEVER: LEB64 will reduce my availabe adressable space per byte down from a max of 128 to 64, down 50%;
This will result in:

- 64bit num (8byte): LEB128=10byte; LEB64=11byte
- 128bit num (16byte): LEB128=19byte; LEB64=22byte

If I move to LEB64, if a number is longer than 133 bits I would have lost the 4 bytes I saved by removing the CHECKSUM. For any number smaller, I save space (at least a byte).

Also: For Element count and offset, I loose my 4byte savings quickly if there are many & large offsets between each other. We are loosing one entire byte per offset as soon as the offset grows larger than 63. Thats a lot of bytes in a large array / object and could loose any and all savings I get

To recap: Saves bytes for values & for small parents. Increases the complexity and mental overhead while probably reduceing computaional overhead for parsing and encoding.
